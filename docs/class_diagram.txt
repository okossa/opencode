================================================================================
                    OPENCODE — DETAILED CLASS DIAGRAM (ASCII)
================================================================================

  This diagram documents the main abstractions, types, and relationships in the
  opencode codebase (packages/opencode/src). OpenCode uses TypeScript namespaces
  with Zod schemas as the primary pattern rather than traditional OOP classes.
  Each "namespace" below acts as a module with its exported types (Info schemas),
  events, error types, and key functions.

  Legend:
    ──────>   "depends on / uses"
    ──|>      "extends / inherits"
    ◇─────>   "aggregates / has-many"
    ◆─────>   "composes / owns"
    - - - ->  "emits event to / subscribes"

================================================================================
  22. DESIGN PATTERNS & ARCHITECTURAL NOTES
================================================================================

  1. NAMESPACE PATTERN
     All modules use TypeScript `namespace` with Zod schemas instead of
     traditional classes. Each namespace exports:
       - Info schema (Zod-validated data shape)
       - Event definitions (BusEvent.define)
       - Error types (NamedError.create)
       - Functions (CRUD operations, business logic)

  2. INSTANCE-SCOPED STATE
     Instance.state<S>(init, dispose?) creates per-directory singleton
     state with automatic lifecycle management. Used by: Session, Agent,
     Provider, Tool, MCP, Bus, Permission, Config, Plugin, LSP, etc.

  3. EVENT-DRIVEN ARCHITECTURE
     Bus (instance-scoped) + GlobalBus (cross-instance) provide type-safe
     pub/sub. Events are defined with Zod schemas for validation.
     Server streams events to clients via SSE.

  4. LAYERED CONFIGURATION
     Config merges from: remote well-known → global → project → custom.
     Deep merge for objects, concatenation for arrays.

  5. PERMISSION MODEL
     Hierarchical permission rules with wildcard pattern matching.
     Evaluated per agent (Ruleset) with ask/allow/deny responses.
     Supports session-scoped approval caching.

  6. PROVIDER ABSTRACTION
     Unified provider interface via @ai-sdk packages.
     Models loaded from models.dev database, merged with config overrides.
     Supports bundled + custom + dynamic providers.

  7. TOOL FRAMEWORK
     Generic Tool.Info interface with init → execute lifecycle.
     Tools request permissions via ctx.ask(). Built-in tools + MCP-bridged
     external tools. Registry pattern for tool discovery.

  8. FILE-BASED PERSISTENCE
     Storage uses atomic file writes with Lock-based concurrency.
     XDG basedir-compliant paths via Global module.
     Schema migration support for data evolution.
